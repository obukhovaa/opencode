## 1. Schema and loader

- [x] 1.1 Add `Extends []string \`yaml:"extends,omitempty"\`` to `Step` in `internal/flow/flow.go`, and a `stepTemplate` type for the inheritable subset. Model the template as its own type rather than reusing `Step`: reusing `Step` would make every future step field inheritable by default, which is the exact failure D4's allow-list exists to prevent.
  - Done, with the type's *purpose* revised alongside the two-part key rule (see 1.4). `stepTemplate` (`internal/flow/include.go`) is still its own type, but it carries provenance plus a `Step` value rather than a hand-listed field subset: `Name`, `Keys` (the template's RAW declared keys — needed so a later template's explicit zero can override an earlier template's value, the same trap as 1.7 one level up), and `step Step` holding the decoded values. Decoding into a `Step` is safe *because* the key rule rejects `id` / `interactive` / `interaction` / `resume_after` by name before the decode runs, and it is what makes a field added to `Step` later inheritable **by default** — the outcome this task's original wording (a curated subset) would have prevented. The stale `Step.MaxTurns` doc comment claiming `>= 1` was corrected while here, per D3.
- [x] 1.2 Add `Include []IncludeEntry \`yaml:"include,omitempty"\`` to `flowFile`, with `IncludeEntry{Local string}`. Decode unknown include kinds (`remote`, `project`) as an error rather than an empty entry — an ignored include leaves `extends` unresolvable and the error would otherwise point at the wrong line.
  - Done via `IncludeEntry.UnmarshalYAML`. Note the error class: because it is raised *inside* `yaml.Unmarshal`, it surfaces wrapped as `ErrInvalidYAML` (with the yaml line number) rather than as `ErrInvalidInclude`; the message still names the bad kinds and points at `local:`. Tests assert `ErrInvalidYAML` for this case accordingly.
  - Fixed after review: the first version reported only the FIRST non-`local` key, so a GitLab-style `project:` + `file:` entry errored with `unsupported include kind "file"` — pointing the author at the wrong line. It now collects and reports every unsupported key, and the `project include kind` subtest asserts `project`, `file` and `local` all appear. A new subtest covers `local:` joined by an unsupported sibling (`ref:`), which is rejected rather than honoured.
- [x] 1.3 In `parseFlowFile`, before `$ref` resolution and `validateFlow`: read each include, apply the per-file size cap, decode its templates, resolve each template's `output.schema` `$ref` against the TEMPLATE's dir, then merge each step's `extends`. Order matters and is asserted by 2.6 — merging after validation would let a template smuggle an invalid step through.
  - Done (`resolveStepIncludes`, called from `parseFlowFile` right before the existing `$ref` loop). The call is entered when the flow declares `include` OR any step declares `extends`, so `extends` with no include fails loudly instead of running an empty step.
- [x] 1.3b Name the mechanism, because the obvious implementation cannot work: the loader does ONE typed `yaml.Unmarshal` (`registry.go:341`), so a step's *raw* keys — which 1.7 needs to decide what overrides — are not available on that path. Either re-parse the flow bytes into a map, merge at map level, and re-decode; or give `Step` a custom `UnmarshalYAML` — but note the second only RECORDS which keys the step declared, for the caller to merge on, since the templates live outside the step's own YAML node and are not reachable from it. Precedent for the first: `validateFlowSessionKeys` (`:352`) already re-parses the original bytes.
  - Chose the re-parse, in a narrower form than the task's first option: `stepRawKeys` re-parses `data` into `[]map[string]yaml.Node` and keeps only the KEY NAMES per step index. The merge then runs on the typed values, so there is no map-level merge and no re-decode — nothing round-trips through YAML, and the typed decode stays the single source of values. Same precedent (`validateFlowSessionKeys`), same input (`data`), so it is likewise unaffected by anything applied later.
  - **The re-parse's hidden cost, found by traceability review and fixed:** the two decodes do not always yield the same number of elements. `yaml.v3` DROPS a null / comment-only sequence entry from a typed `[]Step` decode but KEEPS it as an empty map in the raw one, so `- # placeholder` above a real step shifts the pairing by one; the real step is then handed an empty key set, reads as declaring nothing, and the template overwrites keys it did set — worst case a guard step running an agent its flow does not name, which `validateFlow` cannot see because the dropped entry is absent from the typed tree. Both softening paths are gone: `stepsRawKeysAligned` rejects a count mismatch (`ErrInvalidInclude`, quoting both counts and telling the author to remove empty entries), `stepRawKeys` returns an error instead of a nil slice, and the merge site indexes without a bounds check so a future divergence cannot be silently absorbed. Shapes probed and found NOT to diverge: anchors and aliases, merge keys (`<<:`, whose merged-in keys appear in both decodes and so count as declared by the step), multi-document files (both take the first document), `- {}` (kept by both), and a non-sequence `steps:` (both fail; the typed decode reports it first). Any future divergence is covered by the count guard regardless.
- [x] 1.4 Enforce the allow-list: a template key outside `agent|prompt|session|output|rules|fallback|maxTurns|maxIterations|timeout|compact` is a load error naming the key. Decode templates into a raw map first so an unknown key is *visible* — a typed decode silently drops it, which is how `flow.session` typos used to pass and why `validateFlowSessionKeys` exists.
  - Done as the **two-part rule**, which supersedes this task's allow-list wording (D4 revised after review; the allow-list was the un-propagated older revision, which is why the artifacts disagreed):
    - the key must be a **known `Step` field** — a `promt:` typo, or any key the schema does not model, is a load error naming it and listing the real fields. Templates decode into a raw map first so an unknown key is *visible*; a typed decode drops it silently, which is how `flow.session` typos used to pass.
    - **and** it must not be one of `id` / `interactive` / `interaction` / `resume_after` — each errors naming the key **and quoting why** (the orchestrator reads it out of the same file without resolving templates).
    Both halves are needed: part 1 keeps typo detection, part 2 keeps the cross-repo contract. The observable consequence is that a field added to `Step` later is inheritable **by default** — there is no curated inheritable list. `inheritableStepKeys()` is derived by reflection from `Step`'s yaml tags minus the rejected set, and `mergeTemplates` copies by yaml key through reflection, so a new engine field needs no change in `include.go`. Maintenance friction lands on the small, rarely-changing rejected set instead of the fast-growing engine schema.
    Known limitation, recorded rather than solved: the rule is top-level only — a *nested* field the orchestrator starts reading (e.g. a future `session:` sub-key) rides in inside an inheritable key.
- [x] 1.5 Reject `include` or `extends` inside a template file (D6), and an `extends` naming a template no include provides.
  - Done; three distinct messages (`include` at the template file's top level, `extends` inside a template, unknown template name — the last listing the template names the includes actually provided, which is what diagnoses a missing `.` prefix).
- [x] 1.6 Resolve `local:` include paths against `config.WorkingDir` (root-relative, D5), reusing the base `discoverCustomPathFlows` already uses for relative `flowPaths`. A template's output-schema `$ref` stays relative to the TEMPLATE file's directory — call `format.ResolveSchemaRef` with the template's dir, not the flow's. Document the asymmetry; it is the same split GitLab CI has.
  - Done (`resolveIncludePath`). Nil-safety: uses `config.Get()` + nil check, NOT `config.WorkingDirectory()` (which panics when no config is loaded — several existing `internal/flow` tests call `parseFlowFile` without one). With no config the base is empty and a relative include falls back to the process working directory; absolute paths bypass the base entirely.
  - The spec delta previously said "Include paths MUST resolve relative to the directory of the file declaring them", contradicting D5 and D1's own example. Flagged during implementation and **corrected at the source** (review, 2026-08-03): `local:` resolves against the workspace root, with the `$ref` asymmetry stated in the requirement. The implementation was already root-relative; no code change followed.
- [x] 1.7 Implement the merge: shallow per key, templates left to right, then the step's own keys. Guard the zero-value trap — on a typed struct an explicit zero is indistinguishable from unset, so the step's *raw* keys must decide what overrides, not the decoded values. The affected inheritable fields are `maxTurns`, `maxIterations`, `timeout: ""`, `agent: ""`, `prompt: ""`, and — least obvious — **`session`**, because `Session StepSession` is a value type (`flow.go:57`) so `session: {fork: false}` reads as unset. `compact` is safe (`*StepCompact`, nil is observable). NOT `interactive`: the allow-list forbids it in a template, so it can never be inherited.
  - Done (`mergeTemplates`): iterate `inheritableStepKeys()`; skip any key the step declared (raw keys); otherwise copy the field from the LAST template that declared it. Templates also carry raw keys, so template-over-template override honours explicit zeros too. The copy is by yaml key through reflection (`stepFieldIndexByYAMLKey`) rather than a per-field switch — with the two-part rule, a per-field switch would be a second curated list to forget, and forgetting it would silently drop an inherited value. `interactive` still cannot be inherited: it is in the rejected set.
