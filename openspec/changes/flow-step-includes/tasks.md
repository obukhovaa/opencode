## 1. Schema and loader

- [x] 1.1 Add `Extends []string \`yaml:"extends,omitempty"\`` to `Step` in `internal/flow/flow.go`, and a `stepTemplate` type for the inheritable subset. Model the template as its own type rather than reusing `Step`: reusing `Step` would make every future step field inheritable by default, which is the exact failure D4's allow-list exists to prevent.
  - Done. `stepTemplate` (`internal/flow/include.go`) carries the inheritable fields plus two non-YAML fields: `Name` and `Keys` — the template's RAW declared keys, needed so a later template's explicit zero can override an earlier template's value (same trap as 1.7, one level up). The stale `Step.MaxTurns` doc comment claiming `>= 1` was corrected while here, per D3.
- [x] 1.2 Add `Include []IncludeEntry \`yaml:"include,omitempty"\`` to `flowFile`, with `IncludeEntry{Local string}`. Decode unknown include kinds (`remote`, `project`) as an error rather than an empty entry — an ignored include leaves `extends` unresolvable and the error would otherwise point at the wrong line.
  - Done via `IncludeEntry.UnmarshalYAML`. Note the error class: because it is raised *inside* `yaml.Unmarshal`, it surfaces wrapped as `ErrInvalidYAML` (with the yaml line number) rather than as `ErrInvalidInclude`; the message still names the bad kind and points at `local:`. Tests assert `ErrInvalidYAML` for this case accordingly.
- [x] 1.3 In `parseFlowFile`, before `$ref` resolution and `validateFlow`: read each include, apply the per-file size cap, decode its templates, resolve each template's `output.schema` `$ref` against the TEMPLATE's dir, then merge each step's `extends`. Order matters and is asserted by 2.6 — merging after validation would let a template smuggle an invalid step through.
  - Done (`resolveStepIncludes`, called from `parseFlowFile` right before the existing `$ref` loop). The call is entered when the flow declares `include` OR any step declares `extends`, so `extends` with no include fails loudly instead of running an empty step.
- [x] 1.3b Name the mechanism, because the obvious implementation cannot work: the loader does ONE typed `yaml.Unmarshal` (`registry.go:341`), so a step's *raw* keys — which 1.7 needs to decide what overrides — are not available on that path. Either re-parse the flow bytes into a map, merge at map level, and re-decode; or give `Step` a custom `UnmarshalYAML` — but note the second only RECORDS which keys the step declared, for the caller to merge on, since the templates live outside the step's own YAML node and are not reachable from it. Precedent for the first: `validateFlowSessionKeys` (`:352`) already re-parses the original bytes.
  - Chose the re-parse, in a narrower form than the task's first option: `stepRawKeys` re-parses `data` into `[]map[string]yaml.Node` and keeps only the KEY NAMES per step index. The merge then runs on the typed values, so there is no map-level merge and no re-decode — nothing round-trips through YAML, and the typed decode stays the single source of values. Same precedent (`validateFlowSessionKeys`), same input (`data`), so it is likewise unaffected by anything applied later.
- [x] 1.4 Enforce the allow-list: a template key outside `agent|prompt|session|output|rules|fallback|maxTurns|maxIterations|timeout|compact` is a load error naming the key. Decode templates into a raw map first so an unknown key is *visible* — a typed decode silently drops it, which is how `flow.session` typos used to pass and why `validateFlowSessionKeys` exists.
  - Done, and this is the one place the artifacts disagree, so the resolution is recorded: **proposal + D4 + this task say allow-list; the spec delta says the four keys are rejected by name and "Every other step key is inheritable … Any key added to the flow schema later is inheritable by default".** Implemented as an allow-list (D4's fail-safe direction) with by-name errors layered on top, so both readings are served for today's schema:
    - `id` / `interactive` / `interaction` / `resume_after` → error naming the key **and quoting why** (the orchestrator reads it).
    - any other key not in `inheritableStepKeys` (e.g. a `promt:` typo, or a `Step` field added later) → error naming the key and listing the inheritable set.
    For the current schema the two readings are indistinguishable. They diverge only when a new `Step` field lands: here it is NOT inheritable until added to `inheritableStepKeys`, which contradicts the spec delta's "inheritable by default" sentence. Flagged rather than silently followed — D4 argues the fail-safe direction at length and the error message tells the author exactly what to do.
- [x] 1.5 Reject `include` or `extends` inside a template file (D6), and an `extends` naming a template no include provides.
  - Done; three distinct messages (`include` at the template file's top level, `extends` inside a template, unknown template name — the last listing the template names the includes actually provided, which is what diagnoses a missing `.` prefix).
- [x] 1.6 Resolve `local:` include paths against `config.WorkingDir` (root-relative, D5), reusing the base `discoverCustomPathFlows` already uses for relative `flowPaths`. A template's output-schema `$ref` stays relative to the TEMPLATE file's directory — call `format.ResolveSchemaRef` with the template's dir, not the flow's. Document the asymmetry; it is the same split GitLab CI has.
  - Done (`resolveIncludePath`). Nil-safety: uses `config.Get()` + nil check, NOT `config.WorkingDirectory()` (which panics when no config is loaded — several existing `internal/flow` tests call `parseFlowFile` without one). With no config the base is empty and a relative include falls back to the process working directory; absolute paths bypass the base entirely.
  - Second disagreement recorded: the spec delta says "Include paths MUST resolve relative to the directory of the file declaring them", which contradicts D5 (and D1's own example). Implemented D5 / root-relative, which is also what the migration needs for team-hosted flows. **The spec delta sentence needs correcting before sync.**
- [x] 1.7 Implement the merge: shallow per key, templates left to right, then the step's own keys. Guard the zero-value trap — on a typed struct an explicit zero is indistinguishable from unset, so the step's *raw* keys must decide what overrides, not the decoded values. The affected inheritable fields are `maxTurns`, `maxIterations`, `timeout: ""`, `agent: ""`, `prompt: ""`, and — least obvious — **`session`**, because `Session StepSession` is a value type (`flow.go:57`) so `session: {fork: false}` reads as unset. `compact` is safe (`*StepCompact`, nil is observable). NOT `interactive`: the allow-list forbids it in a template, so it can never be inherited.
  - Done (`mergeTemplates`): iterate `inheritableStepKeys`; skip any key the step declared (raw keys); otherwise take the value from the LAST template that declared it. Templates also carry raw keys, so template-over-template override honours explicit zeros too.
